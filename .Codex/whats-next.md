## Dead Ends

- Render Free services provide no Shell or One-Off Jobs — use the bridge's fixed-purpose actions instead of `bin/rails console`.
- Render environment values are masked in the editor; verify allowlist/config changes through the bridge's `status` action, not the masked UI.
- This worktree has no `config/credentials/staging.key` on disk. Editing staging credentials requires the real `RAILS_MASTER_KEY` (from Render's env vars) `export`ed in the **same terminal** as the edit/show command — a one-off `KEY=... command` prefix does not persist for a later command in the same session. A wrong/malformed key fails two different ways depending on what boots first: `bin/rails credentials:show`/`edit` fails immediately with `AEAD authentication tag verification failed` if the key can't decrypt the target file at all, or fails deeper during app boot with `key must be 16 bytes` if the key string itself isn't valid 32-hex-char format (Honeybadger's initializer touches credentials during boot before the command's own output prints, which is a red herring that looks like a staging problem but is a local key format issue). Always sanity check with `echo -n "$RAILS_MASTER_KEY" | wc -c` (expect `32`) before troubleshooting anything else.
- No `$EDITOR`/`$VISUAL` is set by default; use `VISUAL="zed --wait" mise exec -- bin/rails credentials:edit --environment staging` for this user's preferred editor.
- The Stripe webhook destination's signing secret can silently drift from staging credentials with zero errors until an actual delivery is attempted (manifests as HTTP 400, empty body, from `/webhooks/stripe`). Always compare the destination's revealed secret against credentials directly.
- **Different Stripe accounts can look identical in casual conversation** ("test mode", "sandbox") while being entirely separate — compare the account id embedded in the publishable key (`pk_test_51<account_id>...`) rather than assuming "test mode" means "the same account."
- Specific-commit Render deploys are manual, easy to mis-select from the commit list, and disable auto-deploy. **Always confirm the exact deployed SHA after a deploy**, not just that "a deploy succeeded" — this is very likely the cause of the current blocker.
- A local Pay::Customer/Pay::Subscription row's `processor_id`/`processor_plan` can reference an object that doesn't exist for whatever Stripe account the app's credentials currently point at (stale from an earlier session, a different environment, or a credentials fix made mid-flow). These fail late, inside `CheckoutsController#set_checkout_session`, as `Stripe::InvalidRequestError`, not as validation errors — check Honeybadger or Render logs for the exact message, don't guess.
- Honeybadger did not show a fault for one of the 500s the user hit (checked, nothing new) even though Render logs showed the error was reported successfully seconds later — if Honeybadger looks empty, double check the Render logs directly rather than concluding there's no error.
- A browser attempt to open Stripe was once interrupted while tabs were being moved; the user drives the browser directly now so this shouldn't recur, but reconnect to an existing Chrome session if browser automation is used again.
