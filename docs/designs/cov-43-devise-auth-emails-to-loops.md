# Feature: Wire Devise auth emails to Loops

## Problem

Cove's two active Devise authentication notifications still have no delivery
path to the published Loops templates. Password-reset instructions and
password-change security notices must send the correct Loops payload without
rendering the now-inert ERB email bodies.

## Approach

Implement COV-37's chosen Option A: register a generic `LoopsDelivery`
ActionMailer delivery method and configure an app-owned
`LoopsDeviseMailer < Devise::Mailer` for the two active notifications. The
mailer attaches the Loops transactional ID and JSON-encoded data variables as
internal message headers and calls `mail(..., body: "")`, preventing template
lookup and ERB rendering. `LoopsDelivery` reads those headers and delegates the
API request to the existing `LoopsClient`.

Keep Devise 5.0.4's existing synchronous `deliver_now` behavior. A Loops
failure therefore fails the auth-critical request loudly and remains visible to
Rails and Honeybadger instead of showing a false success. Production selects
the Loops delivery method; staging remains disabled through its existing
`perform_deliveries = false` kill switch until COV-46. Development and test keep
their existing Mailbin and test delivery methods.

## Acceptance Criteria

- Requesting a password reset issues exactly one Loops send using the published
  `reset-password` transactional ID.
- The reset payload contains `recipient_email` and an absolute
  `reset_password_url` built with
  `edit_password_url(user, reset_password_token: token)` from Devise's raw
  token.
- The reset URL test resolves and asserts against the real edit-password route,
  including the token parameter, rather than comparing a duplicated URL string.
- Successfully changing a password issues exactly one Loops send using the
  published `password-changed` transactional ID and `recipient_email`.
- Both sends include the stable idempotency key generated by `LoopsClient`.
- `LoopsClient::RateLimit` and `LoopsClient::UnprocessableContent` propagate
  rather than being swallowed, allowing Honeybadger to report them.
- The two mailer actions pass `body: ""`; their vendored Devise ERB views are
  never rendered and `lib/jumpstart/` remains untouched.
- The existing two-email reset behavior remains: reset instructions are sent
  when requested and a password-changed notice is sent after successful reset.
- `bin/rails test` passes, `bin/rubocop` is clean, and the final `git diff` is
  reviewed.

## Prototype

None. No application UI or email-content redesign is part of this ticket. The
existing password screens remain unchanged, while the published Loops
templates from COV-40 own email content, subject lines, and visual presentation.

## Data Model

No database models, migrations, or user fields change.

Create `config/loops.yml` with shared, checked-in transactional IDs keyed by
the Devise notification names and read it through
`Rails.application.config_for(:loops)`:

```yaml
shared:
  transactional:
    reset_password_instructions: cmsdnzduk02k40jx72rv3uwe2
    password_change: cmsdo8ixv001e0j1zu027i3s7
```

These IDs are non-secret and intentionally diff-reviewable. The Loops API key
remains in environment credentials and continues to be read by
`LoopsClient.client`.

The internal ActionMailer transport contract is:

- `X-Loops-Transactional-Id`: the configured transactional ID.
- `X-Loops-Data-Variables`: a JSON object containing the template variables.

The reset variables are `recipient_email: user.email` and
`reset_password_url: edit_password_url(user, reset_password_token: token)`.
The password-change variables contain only `recipient_email: user.email`.

No idempotency record is stored. `LoopsClient` derives the key from the
transactional ID, recipient, and data variables. A newly generated reset token
therefore produces a distinct send, while a retry of an identical logical send
remains deduplicated.

## Screens / Flows

### Password reset request

1. The user submits their email through the existing `/users/password/new`
   screen.
2. Devise creates and stores a fresh raw reset token.
3. `LoopsDeviseMailer` builds a bodyless `reset-password` message containing
   the user's email and an absolute reset URL for the existing
   `/users/password/edit` route.
4. `LoopsDelivery` synchronously issues exactly one request through
   `LoopsClient`.
5. On success, Devise continues its existing reset-instructions response. On an
   unsuppressed Loops error, the request fails through the existing branded
   server-error path and Honeybadger can observe the exception.

### Password reset completion and account password changes

1. The user submits a valid new password through either the reset form or the
   existing `/account/password` screen.
2. Devise updates the password and triggers its existing `password_change`
   notification.
3. `LoopsDeviseMailer` builds a bodyless `password-changed` message and
   `LoopsDelivery` sends it synchronously.
4. On success, the existing password-change response continues. On failure, the
   exception propagates from Devise's `after_update` callback and the password
   transaction rolls back.

No forms, routes, components, page copy, or application layouts change. Email
content and subjects remain entirely in the published Loops templates.

## Scope

**In:** Generic Loops ActionMailer delivery method and registration; app-owned
Devise mailer override for `reset_password_instructions` and
`password_change`; production delivery-method selection; shared
`config/loops.yml` IDs; exact payload construction; absolute reset URL;
idempotency, propagation, dead-view, and request-flow tests; documentation that
the vendored ERB views are intentionally unreachable.

**Deferred:** AccountMailer integration (COV-44); Pay billing mail integration
(COV-45); changing staging's email behavior (COV-46); live end-to-end inbox
delivery verification (COV-47); enabling `email_changed`, confirmation, unlock,
or any other Devise notification; changing the existing two-email reset
behavior; edits under `lib/jumpstart/`; email copy or visual changes.

## Open Questions

None.

Resolved during design:

- Keep Devise delivery synchronous and fail loudly so users do not receive a
  false success when an auth-critical email was not accepted.
- Preserve both notifications in a completed reset flow: reset instructions
  first, then the password-changed security notice.
- Follow COV-37 Option A through an ActionMailer delivery method and app-owned
  Devise mailer rather than bypassing ActionMailer from `User`.
- Leave vendored Devise ERB views in place but unreachable via `body: ""`.

## More Info

- COV-37 chose a custom ActionMailer delivery method, bodyless mailers, header
  transport for the Loops ID and variables, and `config/loops.yml` for
  non-secret IDs.
- COV-39 provides `LoopsClient`, content-derived idempotency, typed error
  mapping, credentials, and `LoopsMailDeliveryJob`. The retry job applies only
  to `deliver_later`; this ticket deliberately preserves Devise's synchronous
  `deliver_now`, so failures surface immediately rather than retrying in the
  background.
- COV-40 published `reset-password` as
  `cmsdnzduk02k40jx72rv3uwe2` with `recipient_email` and
  `reset_password_url`, and `password-changed` as
  `cmsdo8ixv001e0j1zu027i3s7` with `recipient_email`.
- Devise saves a reset token before invoking the mailer. If the synchronous
  Loops send fails, that undelivered token remains stored; a new reset request
  replaces it with a fresh token.
- `LoopsClient` already treats a 409 idempotency conflict as successful. Other
  delivery errors, malformed Loops headers, invalid variables JSON, or missing
  notification mappings must fail loudly rather than falling back silently.
