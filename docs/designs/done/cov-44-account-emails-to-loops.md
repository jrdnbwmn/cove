# Feature: Wire account emails to Loops

## Problem

`AccountMailer#invite` and `AccountMailer#cancellation_reason` still render
vendored ERB email bodies even though COV-41 published their Loops replacements.
The existing Jumpstart call sites need a host-app delivery path to those
templates without editing vendored code or changing their enqueue behavior.

## Approach

Implement COV-37's chosen Option A by shadowing `AccountMailer` at
`app/mailers/account_mailer.rb`. The two actions attach the configured Loops
transactional ID and JSON-encoded variables as the existing internal headers,
then call `mail(..., body: "")` so Action Mailer never looks up or renders the
vendored templates. The registered `LoopsDelivery` and existing
`LoopsMailDeliveryJob` continue to own HTTP delivery, idempotency, and retries.

Keep both Jumpstart call sites untouched. Invitations continue through
`AccountInvitation#save_and_send_invite` / `#send_invite` and `deliver_later`.
Cancellation continues through the authenticated billing endpoint and
`deliver_later(wait: 1.hour)`.

Use layered tests: focused mailer tests prove the exact message contract; a
model-level invitation test proves the real send boundary; and an integration
cancellation test proves the controller still schedules exactly one delivery
for one hour later and that performing it produces the expected Loops request.

## Acceptance Criteria

- Calling `AccountInvitation#save_and_send_invite` for a valid invitation
  enqueues and performs exactly one Loops send using the published
  `account-invite` transactional ID.
- The invite payload contains exactly `inviter_name`, `account_name`, and an
  absolute `invitation_url` generated by `account_invitation_url(invitation)`.
- The invitation URL resolves through the real account-invitation route and
  includes the invitation token.
- `inviter_name` falls back to `"Someone"` when `invited_by` is nil, matching
  current behavior.
- An invalid invitation does not enqueue a mail job or issue a Loops request.
- Cancelling through the existing authenticated billing endpoint schedules
  exactly one mail delivery for approximately one hour later.
- Performing the scheduled cancellation delivery issues exactly one Loops send
  using the published `cancellation-survey` transactional ID and an empty
  variables object.
- Both messages retain the existing support sender metadata; cancellation also
  retains the support reply-to metadata.
- Both messages have empty, non-multipart bodies and build without rendering
  the vendored ERB views.
- Both Loops requests carry the stable content-derived idempotency key.
- Missing transactional mappings fail loudly rather than falling back to
  another template or provider.
- The obsolete `AccountMailerPreview` is removed because it previews content
  that no longer ships.
- `bin/rails test` passes, `bin/rubocop` is clean, and the final `git diff` is
  reviewed.
- No file under `lib/jumpstart/` changes.

## Prototype

None. No Cove UI or email-content design changes in this ticket. COV-41's
published templates lock the subject, copy, sender identity, Reply-To behavior,
format, and visual presentation.

## Data Model

No database models, migrations, associations, credentials, routes, or
persisted records change.

Add the two shared, non-secret IDs to the existing `config/loops.yml`, keyed by
the `AccountMailer` action names and read through
`Rails.application.config_for(:loops)`:

```yaml
shared:
  transactional:
    reset_password_instructions: cmsdnzduk02k40jx72rv3uwe2
    password_change: cmsdo8ixv001e0j1zu027i3s7
    invite: cmsdr01rw02s00j3ozshehy4f
    cancellation_reason: cmsdrmznp040g0jzsnkt9hpsa
```

The internal Action Mailer transport contract remains:

- `X-Loops-Transactional-Id`: the configured transactional ID.
- `X-Loops-Data-Variables`: a JSON object containing the template variables.

The payload mappings are:

| Action | Top-level recipient | Data variables |
| --- | --- | --- |
| `invite` | `account_invitation.email` | `inviter_name`: `account_invitation.invited_by&.name || "Someone"`; `account_name`: `account_invitation.account.name`; `invitation_url`: `account_invitation_url(account_invitation)` |
| `cancellation_reason` | `user.email` | Empty object |

Both Action Mailer messages retain the existing support `from` metadata, and
`cancellation_reason` retains its support `reply_to` metadata. `LoopsDelivery`
does not transmit those mail headers; the actual delivered From and Reply-To
values remain owned by the published Loops templates, where COV-41 verified
them in a real inbox.

No idempotency record is stored. `LoopsClient` derives a stable key from the
transactional ID, recipient, and variables, so duplicate job execution is
suppressed without new persistence.

## Screens / Flows

### Account invitation

1. Existing code calls `AccountInvitation#save_and_send_invite` or
   `#send_invite`.
2. The unchanged Jumpstart model invokes the host-app `AccountMailer#invite`.
3. The mailer builds a bodyless message for the invitation email with the
   `account-invite` ID and its three required variables.
4. `deliver_later` enqueues the existing `LoopsMailDeliveryJob`.
5. When performed, `LoopsDelivery` issues exactly one idempotent request through
   `LoopsClient`.

The invitation UI remains gated by Cove's personal-account configuration.
COV-44 does not change `account_types`, enable the UI, or add a new route.

### Subscription cancellation

1. An account admin cancels through the existing billing endpoint.
2. The unchanged Jumpstart controller schedules
   `AccountMailer#cancellation_reason` for one hour later.
3. The mailer builds a bodyless message for the cancelling user with the
   `cancellation-survey` ID and an empty variables object.
4. After the delay, the existing delivery job sends the idempotent Loops
   request.

No application screen, form, component, route, visible copy, or layout changes.
The `account-invite` email remains Styled with the existing Cove theme and its
invitation button. The `cancellation-survey` remains a Plain, reply-oriented
email.

## Scope

**In:** Host-app `AccountMailer` shadow for `invite` and
`cancellation_reason`; two checked-in transactional mappings; exact payload and
address metadata; absolute invitation URL; inviter fallback; bodyless delivery;
idempotency assertions; model-level invitation coverage; controller-level
cancellation scheduling coverage; removal of the obsolete account-mailer
preview; and dead-view documentation/tests.

**Deferred:** Devise authentication mail (COV-43); Pay billing mail (COV-45);
guarded staging enablement (COV-46); live eleven-message staging verification
(COV-47); changing `account_types`; enabling or redesigning invitation UI;
email copy or template changes; production activation; and any edits under
`lib/jumpstart/`.

## Open Questions

None.

Resolved during design:

- Use COV-37 Option A and shadow only `AccountMailer`; do not override either
  vendored call site.
- Exercise invitations at the real model send boundary rather than through the
  currently gated UI. Plain `AccountInvitation.create` is not itself a send
  trigger; `save_and_send_invite` is.
- Exercise cancellation through the authenticated controller flow so the test
  proves the vendored one-hour scheduling contract.
- Make no staging configuration changes. Staging now uses `:async`, which
  supports scheduled jobs; COV-46 separately owns guarded live delivery.
- Leave vendored ERB views in place but unreachable via `body: ""`, and delete
  only the obsolete host-app preview.
